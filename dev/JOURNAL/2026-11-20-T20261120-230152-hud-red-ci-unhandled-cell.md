# T20261120-230152: HUD red-CI cell for unhandled failed runs (n362 step 1)

## TLDR

- **Type**: feature
- **Problem**: on 2026-11-20 Nightly Orchestrator and Upstream Sync went red at 06:06Z and nobody noticed for ~10 h; the HUD `ci` cell watches one workflow only.
- **Solution**: `hud/scripts/hud-redci.sh` counts unhandled failed runs (default branch or schedule, any workflow) of the repos registered in the HUD config and the band shows `✗ N unhandled CI` in the red top row.

## Problem

- Evidence: r1339 analysis (job 1339): the `ci` cell reads `.[0]` of ONE workflow (`hud/scripts/hud-ci.sh`), so Upstream Sync and Tests reds were invisible, and a later green dispatch hid a red schedule run.
- Impact: a red CI that blocks the nightly release sat unseen for ~10 hours.

## Context

- Owner decisions (2026-11-20, replace the first defaults):
  - watched repos = ONLY the repos registered in the HUD config, today `ci.repo` (synxdb-build-pipeline); never the session repo (ccxp-skills);
  - red is red: any failing workflow on the default branch or schedule counts, Upstream Sync and Tests included;
  - overnight and idle coverage = T20261120-154507 and T20261120-105513; no `ci-red` issue workflow.
- Existing pattern: `hud/scripts/hud-ci.sh` (cache, TTL, detached refresh, lock dir, untrusted JSON), `isCiRed` and the top row in `hud/model.ts`.

## Solution

- `hud/scripts/hud-redci.sh` (verified by `tests/hud_redci.bats`): per repo one cached, detached `gh run list --status failure`; a repo lookup and a success listing only when something failed; drop runs superseded by a later success of the same workflow and branch, or handled (run id in `ccxp-context/`, the ledger or `dev/TODO/`); 7-day window.
- Config: `redci: {repos: [...]}` in the HUD config (`hud/config.ts` `parseRedci`, `redciRepos`); unset means the `ci.repo` repo, an empty list switches it off; `hud/register.tsx` passes the list to `hud-data.sh`.
- Band: `hud/model.ts` `redciVariants` and `ciRow`: the red-CI cell shares the top row with the `ci` cell, all segments `alert`.
- Alternatives rejected:
  - one call without `--status` (also gives successes): lists 50+ runs every refresh; the failure-only call is the cheap common path;
  - defaulting to the session repo: the owner ruled it out.
