# T20260924-159109: Design /skill-to-app — compile a matured skill's deterministic steps into a program

## TLDR

- **Type**: research
- **Problem**: a mature skill still pays LLM-token cost every invocation
  re-reading/re-interpreting steps that need no judgment.
- **Solution**: no new `/skill-to-app` skill or compiler is needed — the
  mechanism already exists as `skill-conventions` §9 ("Deterministic logic →
  bundled scripts") and the §10 maturity ladder already provides the
  "mature enough" bar. This task's deliverable is wiring those two sections
  together explicitly and filing the one real gap found (drift detection)
  as a follow-up, not building new tooling.

## Problem

- A mature, stable skill (fixed control-flow, low-branching, deterministic
  steps) still pays LLM-token cost every invocation to re-read and
  re-interpret its full `SKILL.md` instructions, even for the parts that
  never actually require judgment.
- Originally filed as a request to design a `/skill-to-app` skill that
  takes a matured skill's instructions and offloads the
  deterministic/procedural logic to a compiled script or small program,
  reserving the model's token budget for the genuinely flexible,
  judgment-requiring parts.

## Context

- This exact problem was already solved once, concretely:
  `dev/JOURNAL/2026-09-22-T20260914-359646-todo-next-as-local-script.md`
  ported `/todo list`'s table-rendering and `/todo next`'s queue-walk into
  `todo/scripts/{_lib,todo-list,todo-next}.sh`
  (`todo/SKILL.md:83-85`, `:126-128`: *"Run ... and print its output
  verbatim ... no judgment involved ... costs no model call"*), while
  deliberately keeping `sweep`'s judgment-call logic (blocker-order
  enforcement, Park recommendations) in prose.
- That one-off was generalized into a standing convention:
  `skill-conventions/SKILL.md:72-80`, **"9. Deterministic logic → bundled
  scripts"** — port a fully deterministic/mechanical workflow step into
  `<skill>/scripts/`, keep real judgment calls in prose, and gate the
  switchover on a behavior-parity test (`:78`).
- Other skills already apply §9 independently: `address-pr/scripts/{auto-
  pick,pre-merge-check}.sh` (`address-pr/SKILL.md:173`: *"the single source
  of truth for CI, test plan, and pipeline verification"*, but explicitly
  **not** a judgment substitute — `:161` routes back to
  `superpowers:verification-before-completion` before trusting it),
  `design-score/scripts/score.sh` (`design-score/SKILL.md:15-18`:
  *"deterministic only ... no LLM rubric"*), and
  `quality-probe/scripts/probe.sh`.
- `skill-conventions/SKILL.md:92-98`, **"10. Quality loop" — Maturity
  ladder** already answers this task's first open question ("what makes a
  skill mature enough, who decides"): a skill reaches L3 Practitioner
  (latest eval run ≥ 90%) or L4 Master (score ≥ 85, last 3 runs ≥ 90%, zero
  open feedback items) via `skill_score.py`/`skill_eval.py` — **computed,
  never self-declared** (`:92`). §9 itself doesn't yet cite this ladder as
  its extraction bar, which is the actual gap.
- `drive/SKILL.md:238-310` Phase 3.1's sequential `Workflow` (`agent()`
  stages, no `parallel()`) is a *different* mechanism solving a *different*
  problem: it compiles **control-flow** among steps that still each need a
  full model call (design/implement/test/verify), not steps that need
  **zero** model call. §9 extraction and Phase 3.1 Workflow-authoring are
  complementary, not competing answers to this task's third open question.

## Solution

Resolve the task's five open questions against what already exists, rather
than building a new `/skill-to-app` skill or "compiler":

1. **Maturity bar, who decides** → already answered by §10's ladder
   (`skill_score.py`/`skill_eval.py`, computed not self-declared). Action:
   add one cross-reference line in §9 recommending L3+ (ideally L4) as the
   bar before extracting a step to `scripts/` — today §9 and §10 don't cite
   each other even though they're the same mechanism's two halves.
2. **Drift risk** → §9's existing parity-test gate (`:78`) only checks
   correctness *at the moment of the port*; nothing re-checks that a later
   SKILL.md prose edit and its already-ported script haven't silently
   diverged. This is the one real, unaddressed gap found. Rejected for
   this task: building a drift-detection check now (out of scope for a
   `3`-point design task, and `skill_score.py`'s `untested_scripts()`
   check at `skill-conventions/scripts/skill_score.py:109` is the nearest
   existing hook but doesn't do staleness comparison). Filed as a
   follow-up instead (see Done criteria).
3. **Relationship to the `Workflow` tool** → not an either/or. §9
   eliminates the model call entirely for a deterministic step; `drive`
   Phase 3.1's `Workflow` keeps the model call but compiles the
   *sequencing* around it. A skill can use both for different steps.
   Action: add a one-line disambiguation note to §9 so a future author
   doesn't conflate the two.
4. **Hand-back-to-model interface** → already the de facto pattern across
   every §9 example: the script either (a) emits a terminal result the
   skill prints **verbatim** (`todo-list.sh`/`todo-next.sh`), or (b) emits
   a structured pass/fail the skill prose branches on
   (`pre-merge-check.sh`'s `✅ ALL CHECKS PASSED` / `❌ BLOCKED`, which
   routes back into prose-driven fix steps). No new interface needed —
   document this as the two existing shapes rather than invent a third.
5. **Relationship to `skill-conventions`** → it already lives there (§9 +
   §10). No separate lifecycle stage or new skill required.

**Alternatives considered and rejected:**

- **Build a new `/skill-to-app` skill** that mechanically scans a
  `SKILL.md` and proposes script extractions — rejected: §9 already
  documents the convention and the real cost is human judgment ("is this
  step truly judgment-free") and parity-test authoring, neither of which a
  scanner can safely automate away; a mis-extracted judgment call silently
  removes the model's ability to course-correct, worse than paying the
  token cost.
- **A general "compiler" or IR for skills** (parse SKILL.md →
  deterministic program with model-callback hooks) — rejected: over-
  engineered for the actual failure mode observed (a handful of skills
  with one or two genuinely deterministic steps), and `skill-conventions`
  §9's manual-port-plus-parity-test approach has already shipped in 4+
  skills with no tooling investment.
