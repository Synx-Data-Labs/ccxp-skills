# T20260922-453135: Add `/eta` skill — estimate time-to-completion for the current task on hand

## TLDR

- **Type**: feature
- **Problem**: no skill answers "when will the current task likely finish" —
  the user has to manually read `estimation:` and do date math.
- **Solution**: a `scripts/eta.sh` that resolves the current task (explicit
  `T<id>` or `claimed_by` match for this clone), derives a start time from
  the git commit that set `claimed_by` (`git log -S`), converts the
  `estimation:` bucket to a duration, and prints elapsed / remaining /
  projected-finish in the local timezone (override via `--tz`).

## Problem

- No existing skill reports "when will the current task likely be done" — a
  user mid-`/drive`/`/claim` session has no quick way to see this without
  manually reading the task file's `estimation:` and doing date math
  themselves.
- Maintainer ask (this conversation, 2026-09-22): a `/eta` skill that
  estimates time-of-finishing the current task, computing a projected
  finish time from the task's `estimation:` frontmatter and elapsed time so
  far, and defaulting to the local system timezone (optionally overridable
  to a different timezone).
- Basis for the estimate (maintainer-specified): the task's own
  `estimation:` field plus elapsed time since work started (not just a
  static "now + remaining estimation" with no elapsed-time awareness).
- Done looks like: `/eta` (no argument) identifies the current task (the
  one this clone holds via `claimed_by`, or an explicit `T<id>` argument),
  reads its `estimation:` and a start-time signal, computes elapsed vs.
  remaining, and reports a projected finish time in the local system
  timezone by default — with an optional argument to report in a different
  timezone instead.
- **`claimed_by` itself carries no timestamp** (verified against
  `_session/task_claim.sh:521-539` — `_tc_acquire` only ever writes the
  claimant identity string, never a time) — so the "start time" has to come
  from somewhere else: the git commit timestamp of whichever commit set
  `claimed_by` on this task (every task pickup in this repo's convention
  lands a dedicated claim PR first, so that commit's timestamp is a
  reliable proxy for "when work started"), found via
  `git log -S"claimed_by: <claimant-id>" --format=%aI -- <task-file>` (last
  match). Design phase should confirm this holds for every pickup path
  (`/drive` Phase 1, `/claim`, `/address-pr`'s `free`-verdict claim) before
  committing to it.
- **Known bypass this derivation doesn't cover**: `drive/SKILL.md`'s
  `CCXP_PEER_MODE=0` opt-out (verified — line 116) flips only `status:`
  on claim, never touching `task_claim.sh`/`claimed_by` at all — so a repo
  running with peer mode disabled would have no `claimed_by`-setting commit
  for the `git log -S` search to find, and this start-time derivation
  silently returns nothing. `/eta` needs an explicit fallback for that case
  (e.g. the claim-branch's first commit by name convention, or just report
  "start time unknown, showing remaining estimation only") rather than
  failing silently.

## Context

- `_session/task_claim.sh` already tracks `claimed_by`/`claimed_role` per
  task — the source for "which task is current," but not "when did work
  start" (no timestamp field exists; see the Problem section's note on
  deriving start-time from the claim commit instead).
- `repo-conventions/templates/task.md`'s `estimation:` field
  (`15m|30m|1h|2h|4h|1d|2d|1w`) is the existing bucketed-estimate schema
  this skill should read, not reinvent.
- No repo script currently converts an `estimation:` bucket to a duration
  (verified: `grep -rln estimation --include="*.sh" .` → only
  `_session/lint_frozen.sh`, `design-score/scripts/score.sh`,
  `retro/scripts/estimation-revisions.sh`, `todo/scripts/todo-list.sh`, none
  of which do bucket→duration math) — `/eta` is the first consumer and owns
  this mapping.
- Existing skills with computation (not pure prompt-instructions) ship a
  `scripts/*.sh` invoked from a thin `SKILL.md` — e.g.
  `design-score/scripts/score.sh` (`design-score/SKILL.md:30`). `/eta`
  follows the same shape rather than being pure LLM-driven date math (which
  would be non-deterministic and untestable).

## Solution

- New `eta/` skill directory: `eta/SKILL.md` (thin usage doc) +
  `eta/scripts/eta.sh` (the actual logic — deterministic, BATS-testable).
- **Task resolution**: `eta.sh [T<id>] [--tz <IANA-zone>] [--repo-root DIR]`.
  - Explicit `T<id>` arg → resolve via the same file-lookup convention
    `task_claim.sh` uses (`_tc_find_file`, `_session/task_claim.sh:~200s`).
  - No arg → resolve via `task_claim.sh claimant-id`, then grep
    `dev/TODO/*.md` frontmatter for `claimed_by:` matching that id (same
    convention the statusline script already uses —
    `statusline-setup/scripts/statusline-command.sh`).
  - No match either way → exit 1 with `no current task` (clear message, not
    a silent empty output).
- **Start-time derivation**: `git log -S"claimed_by: <claimant-id>" --format=%aI -- <task-file>`,
  last match (oldest commit that introduced this claimant's `claimed_by`
  line — matches how every claim path lands it, per Context above). Falls
  back to "start time unknown — showing remaining estimation only" (no
  elapsed/projected-finish math) when:
  - `git log -S` finds no match (covers the `CCXP_PEER_MODE=0` bypass this
    task's Problem section calls out — no `claimed_by`-setting commit
    exists to find), or
  - the task file isn't tracked by git yet (a brand-new, uncommitted claim).
- **Duration mapping** (bucket → literal wall-clock duration — the simplest
  well-defined reading, since no existing convention in this repo defines
  bucket semantics as workday-relative): `15m`→15m, `30m`→30m, `1h`→1h,
  `2h`→2h, `4h`→4h, `1d`→24h, `2d`→48h, `1w`→7d. Documented as an assumption
  in `eta/SKILL.md` — a future task can swap in workday-aware math if that
  turns out to matter more.
- **Output**: elapsed (start-time to now), remaining (duration − elapsed,
  floored at 0 and flagged `overdue by <Δ>` if negative), and projected
  finish = start-time + duration, rendered in the local system timezone
  (`date` with no `TZ` override) by default, or the `--tz` zone when given
  (validated via `TZ=<zone> date` — an invalid zone exits 2 with a clear
  error rather than silently defaulting).
- **Alternatives considered and rejected**:
  - *Store an explicit `started:` timestamp in frontmatter at claim time* —
    rejected: touches `task_claim.sh`'s claim-PR path (a shared,
    peer-mode-critical script) for every future claim, for a benefit
    `git log -S` already gets for free from data that's already there; more
    surface area to break fleet-wide for a read-only feature.
  - *Pure LLM/no-script estimation ("just have Claude eyeball it")* —
    rejected: non-deterministic, untestable with BATS, and this repo's
    convention for computed values is a script (see Context).
  - *Workday-relative duration math (1d = 8 working hours, skip weekends)* —
    rejected for v1: materially more complex (business-hours calendar,
    holiday awareness) for a feature whose whole point is a quick estimate;
    literal wall-clock duration is honest about its own approximation and
    cheap to build correctly today.
